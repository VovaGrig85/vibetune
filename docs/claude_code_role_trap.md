# Ловушка с полем role в логах Claude Code

## В чём ловушка

Claude Code хранит историю сессии построчным JSON (JSONL), по файлу на сессию, в
`~/.claude/projects/<кодированный путь проекта>/<session-uuid>.jsonl`. У каждой
строки есть `message.role`, и значение `"user"` там получают ДВЕ разные по смыслу
вещи:

1. настоящая реплика, которую напечатал человек;
2. результат вызова инструмента (`tool_result`), который харнесс дописывает в
   историю от имени роли `"user"` — так устроен сам протокол Anthropic Messages
   API, на котором построен Claude Code: результат инструмента возвращается в
   следующем сообщении с ролью `user`, потому что с точки зрения модели это
   очередной вход, а не её собственная реплика.

Если взять `field_map.role = "message.role"` и `user_role_value = "user"` —
самый очевидный, «естественный» выбор — каждый ответ инструмента (а их на порядок
больше, чем реплик человека) засчитывается как реплика человека. Ломается сразу
всё: число реплик человека, доля коротких директивных правок, сегментация на
эпизоды (граница эпизода отчасти зависит от того, when человек заговорил), цепочка
«тихих сбоев» (она сбрасывается репликой человека) — и внешне отчёт при этом
выглядит совершенно нормальным: числа есть, они разумного порядка, ничего не
падает. Это и есть тот самый случай, ради которого в проекте есть правило
«молчаливая неправда опаснее падения».

Второй слой той же ловушки: у Claude Code есть служебные «синтетические»
сообщения — например, результат слэш-команды (`<local-command-stdout>Set model
to...`) — которые тоже формально `message.role == "user"` и тоже содержат обычную
строку в `content`, но напечатаны не человеком, а самим харнессом в ответ на
команду. Признак «content — это строка, а не список блоков» их не отсекает.

## Как нашёл

Открыл реальный транскрипт (`~/.claude/projects/.../*.jsonl`) и построчно
проверил, что `message.content` бывает либо строкой (похоже на реплику), либо
списком из ровно одного блока определённого типа (`thinking`, `tool_use`,
`text`, `tool_result`). Разложил "user"-строки на две группы по типу content и
увидел резкий перекос: например, в одном файле — 165 строк с `type: "user"`, из
них content-строкой (а не списком блоков) — всего 13, остальные 152 —
`tool_result`. То есть при наивном `role == "user"` реплик человека оказалось бы
почти в 13 раз больше, чем есть на самом деле.

## Как проверил, что дело в этом

Сравнил полный набор полей у строки с настоящей репликой человека и у строки с
tool_result — они отличаются набором ключей (`permissionMode`/`origin`/
`promptSource` у настоящей реплики против `toolUseResult`/
`sourceToolAssistantUUID` у результата инструмента), но НЕ отличаются по
`message.role` — оба `"user"`. Дальше проверил гипотезу количественно на второй,
независимой сессии того же профиля — соотношение подтвердилось (1 реальная
реплика на ~11 tool_result-строк).

## Какой признак действительно работает

Поле `promptSource`: оно равно `"sdk"` **только** у строк, где `message.content`
— обычная строка, напечатанная человеком, и отсутствует у tool_result-строк и у
синтетических строк слэш-команд. Проверка на двух разных сессиях (13 реальных
реплик в одной, 1 — в другой) дала стопроцентное совпадение: `promptSource ==
"sdk"` встречается ровно там и только там, где текст на самом деле напечатан
человеком.

Итоговый `field_map` для Claude Code:

```json
{
  "role": "promptSource",
  "user_role_value": "sdk",
  "content": "message.content"
}
```

Это не следует читать как «на Claude Code поле роли называется `promptSource`»
— название вводит в заблуждение. Смысл в другом: **не доверяй очевидному полю
`role` на слово** — ищи то поле (неважно, как оно называется), значение которого
отличает «это напечатал человек» от «это сгенерировано автоматически», и клади
в `user_role_value` именно его. Отсюда и общее предупреждение, добавленное в Шаг
1 промпта для всех будущих харнессов.
